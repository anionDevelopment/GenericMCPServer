# Release notes

## Changes

- An mcp-server offers **resources** next to its tools: content which a client reads by a uri (`resources/list` and
  `resources/read` of the MCP-protocol). A resource is declared in the `resources` of its mcp-server with the uri it is
  read by, its `resource-name`, its `type`, its `mime-type` and - for a script - its `calls`, and it is implemented by
  a python-script, a shell-script or a web-request, exactly like a tool
- A resource takes no parameter: its uri is the whole request. The script which implements it receives that uri as
  `--uri=<uri>`, so one script can implement several resources
- A resource of the type `web-request` is requested from its own uri and declares no `allowed-urls`; its answer is the
  body of the request and not the json-document with the status-code which a tool of that type answers with, and an
  answer whose status-code is no success is a failed read and not a content
- A read which did not work is answered as an error of the protocol with the message of the failure (and not as a
  result with an error-flag and the status-code 502, which is how a failed tool-call is answered), because a client
  which asked for a document must not receive the reason of a failure as if it were that document
- An mcp-server which declares no resource does not claim the resources-capability of the protocol at all
- Subscriptions and uri-templates for resources are not part of this: a resource is declared with the uri it has, and a
  declaration whose uri contains a template-expression makes the server fail while starting
- The virtual environment of a python-resource is named `resource.<resource-name>`, so a resource and a tool of the
  same name do not share one environment
- An mcp-server offers **prompts** next to its tools and resources: a text which a client asks for by its name and
  hands to the model behind it (`prompts/list` and `prompts/get` of the MCP-protocol). A prompt is declared in the
  `prompts` of its mcp-server with its `prompt-name`, its `type`, its `description`, its `calls` and the `parameters`
  it takes
- The values of the arguments of a prompt come from the client and reach the script in exactly the same way as the
  values of a tool (one token per value in the form `--<name>=<value>`, no shell involved); every declared argument is
  offered to the client as a required one
- What the script of a prompt writes is the text of the prompt, handed over as one message of the role `user` together
  with the declared description
- A prompt is implemented by a python-script or a shell-script and never by a web-request: such a declaration takes the
  address it requests either from the client (a tool) or from its own uri (a resource), and a prompt has neither, so a
  prompt which states that type makes the server fail while starting
- A prompt which could not be built is answered as an error of the protocol with the message of the failure, exactly
  like a failed read of a resource and for the same reason: a client which asked for a text must not hand the reason of
  a failure to its model as if it were that text
- An mcp-server which declares no prompt does not claim the prompts-capability of the protocol at all
- A prompt-name which is declared twice within one mcp-server makes the server fail while starting; two mcp-servers may
  use the same prompt-name, because a prompt-name is unambiguous within its mcp-server and not beyond it
- The virtual environment of a python-prompt is named `prompt.<prompt-name>`, so a prompt and a tool of the same name do
  not share one environment
- Neither an optional argument, nor a description per argument, nor a notification when the list of the prompts changed
  is part of this
- An argument of a prompt offers the values it can have (`completion/complete` of the MCP-protocol). They are declared
  in the `completions` of that prompt, keyed by the name of the argument, so an argument has one provider of its values
  or none; the key has to be one of the `parameters` of that prompt
- The values are written by a python-script or a shell-script which is told which argument it is asked about
  (`--argument=<name>`) and which value was entered so far (`--value=<value>`, empty when nothing was entered yet) and
  which writes one value per line; empty lines are dropped. It receives both in exactly the same way in which a tool
  receives the values of its parameters, so one script can complete the arguments of several prompts
- At most 100 values are handed to the client, which is the limit the protocol states, and how many there are in total
  is handed over with them, so that a client can tell a complete list from a cut off one
- An argument which declares no completion and a reference which names no prompt of the mcp-server are answered with no
  value and not with a failure: "which values are possible" is a question a client may ask about anything
- A completion which did not work is answered as an error of the protocol with the message of the failure, exactly like
  a failed read of a resource and a prompt which could not be built
- A completion is implemented by a python-script or a shell-script and never by a web-request, and it declares neither
  `parameters` (the mechanism states which values its script receives) nor a `description` (a client asks for the
  values of an argument it already chose and never chooses a completion itself); such a declaration makes the server
  fail while starting
- An mcp-server which declares no completion does not claim the completions-capability of the protocol at all
- A completion of a resource is not part of this: it would complete a variable of a uri-template, and this server
  declares every resource with the uri it has and derives none from a template - such a request is therefore answered
  with no value
- The virtual environment of a python-completion is named `completion.<prompt-name>.<argument-name>`, so a completion
  and a tool, a resource or a prompt of the same name do not share one environment
- A tool offers the shape of its answer: it declares an `output-schema` (a json-schema) in its declaration, that
  schema reaches the client as the `outputSchema` of that tool, and what the script wrote is handed over as the
  `structuredContent` of the result of `tools/call`
- The text of the answer stays part of the result next to the structured content, so a client which reads no
  structured content receives exactly what it received before, and a tool which declares no schema is unaffected and
  answers with text alone
- An answer which is no json-document or which does not fit the declared schema is a failed tool-call whose message
  states what did not fit (with the http-status-code 502, like every other failed tool-call), because a client which
  was promised data of a known shape must not receive something else under that promise
- A declared schema has to be a json-object and has to be a usable json-schema; it is built while the server starts,
  so a schema which is not usable makes the server fail while starting instead of letting every answer pass
- What the schema allows is what the answer may be, so the declaration decides itself whether the answer is a
  json-object, a list or something else. A tool of the type `web-request` can declare one as well, for the
  json-document with the status-code and the body which such a tool answers with
- Only a tool declares such a schema: a resource states the `mime-type` of its content, a prompt writes the text of
  the prompt and a completion writes one value per line, so an `output-schema` in one of those declarations makes the
  server fail while starting
- A tool-call which its client cancelled is stopped while it runs (`notifications/cancelled` of the MCP-protocol): the
  script behind that call is ended together with everything it started, and a web-request which is waiting for a
  foreign service is aborted
- A declared tool needs nothing for that: it takes no additional parameter, it sends nothing back and it does not even
  learn that it is cancellable
- A cancellation may only stop a call of the same mcp-server and of the same client. The notification states nothing but
  a request-id, and such an id is only unambiguous within the client which chose it, so which mcp-server and which
  client are meant is taken from the request the notification arrived with - a client can therefore not name the call of
  another client, and a cancellation which was sent to one mcp-server does not stop a call at another one
- A cancellation which names a call that is not running stops nothing and is no failure, because a client cancels a call
  it has no answer for yet: a call which ended in the meantime is exactly the case of a cancellation which arrives too
  late
- A cancelled call is answered with that reason and with the http-status-code of a normal answer, and not with the 502
  of a failed tool-call: the 502 states that the program behind this server failed, and nothing failed when the client
  itself stated that it does not want the result anymore
- Only a tool-call is cancelled. A read of a resource, a prompt and a completion are answered in one go, and the
  notification names a request-id and not what that request was about, so a cancellation which names one of them stops
  nothing
- Which call was stopped is written to the log of the server, because a notification is answered with nothing at all and
  would otherwise leave no trace
- The package-references `Microsoft.IdentityModel.Tokens`, `Swashbuckle.AspNetCore.SwaggerGen` and
  `Swashbuckle.AspNetCore.SwaggerUI` are pinned to exactly one version (`[<version>]`) in both projects of
  GenericMCPServerBackend, like every other package-reference of this repository. They were declared as a
  version-range before, which made the build not reproducible and let the linting of the codeunit fail
