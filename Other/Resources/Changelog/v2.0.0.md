# Release notes

## Changes

- An mcp-server offers **resources** next to its tools: content which a client reads by a uri (`resources/list` and
  `resources/read` of the MCP-protocol). A resource is declared in the `resources` of its mcp-server with the uri it is
  read by, its `resource-name`, its `type`, its `mime-type` and - for a script - its `calls`, and it is implemented by
  a python-script, a shell-script or a web-request, exactly like a tool
- A resource takes no parameter: its uri is the whole request. The script which implements it receives that uri as
  `--uri=<uri>`, so one script can implement several resources
- A resource of the type `web-request` is requested from its own uri and declares no `allowed-urls`; its answer is the
  body of the request and not the json-document with the status-code which a tool of that type answers with, and an
  answer whose status-code is no success is a failed read and not a content
- A read which did not work is answered as an error of the protocol with the message of the failure (and not as a
  result with an error-flag and the status-code 502, which is how a failed tool-call is answered), because a client
  which asked for a document must not receive the reason of a failure as if it were that document
- An mcp-server which declares no resource does not claim the resources-capability of the protocol at all
- Subscriptions and uri-templates for resources are not part of this: a resource is declared with the uri it has, and a
  declaration whose uri contains a template-expression makes the server fail while starting
- The virtual environment of a python-resource is named `resource.<resource-name>`, so a resource and a tool of the
  same name do not share one environment
