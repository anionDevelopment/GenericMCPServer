# Release notes

## Changes

- Removed the environment-variable `InitialToolDefinitionsFile` and replaced it with a persisted configuration-value
  `ToolDefinitionsFile`, which defaults to `./Tools.json` (relative to the configuration-folder) the first time the
  configuration-file is generated. An administrator who wants the declaration somewhere else changes that value in the
  configuration-file afterwards instead of having to redeploy with a different environment-variable
- Adapted the documentation and the minimal docker-compose example accordingly
- Fixed a timing-defect in the integration-test-harness: for a test-run, GRYLibrary wipes and recreates the
  configuration-folder between the initialization- and the functional-phase of the server, so a callback which wrote
  the example tool-definitions-file during initialization had it silently discarded before the server ever read it.
  The callback now fires at the start of the functional-phase instead, after that folder is settled
- Moved every decision about who may reach what and about the administration of clients, roles and tokens into
  `BusinessLogicService`: `AccessTokenValidatorMiddleware`, `AdminController` and `ClientAdministrationController` now
  only call it and map its result to a response, instead of deciding those things themselves. This closes the gap
  found while verifying the `architecture` specification, where an adapter towards a protocol decided a domain-question
  on its own
- Corrected the `tool-definitions` specification: a configured tool-definitions-file which does not exist at its
  resolved location was documented as an error which fails startup, while the server has always started with no tool
  offered in that case (the same as when no file is configured at all) - which is the deliberate and now specified
  behavior
- Raised the pinned `GRYLibrary`-version to `2.0.33`: the integration-test-harness starts the real server with
  `ListenOnEveryIP` set (so that a testcase can reach it under `127.0.0.1` without resolving the configured domain),
  and before that version the api-server bound every ip in a test-run regardless of that setting, which made windows
  ask whether the process may communicate in the network on every single test-run - a dialog nobody can answer in an
  unattended run

## Migration

- A configuration-file which already exists is loaded as it is: no value is added to it, and there is no migration of
  configuration-files. A configuration-file which was generated by an earlier version therefore does not contain
  `ToolDefinitionsFile`, and the server does not start with it. Add the element to the application-specific part of the
  configuration-file before the new version is started, with the path of the declaration relative to the
  configuration-folder (the concrete type belongs at the element, the way every other path in that file states it):

  ```xml
  <ToolDefinitionsFile xsi:type="RelativeFilePath">
    <FilePath>./Tools/Tools.json</FilePath>
  </ToolDefinitionsFile>
  ```

- Remove the environment-variable `InitialToolDefinitionsFile` from the deployment. It does not exist any more, neither
  as a commandline-parameter nor in the entry-point of the image, and it is ignored without a message
- Nothing has to be moved: the declaration and the scripts beside it stay where they are, because their location is
  what the new value states. The files of the clients, roles, assignments and tokens are unchanged, as is the form of
  the declaration itself
- A declaration-file which does not exist at the resolved location no longer stops the start: an empty one is created
  and the server offers no tool. A mistake in that path is therefore not visible as a failed start any more. After the
  upgrade, the line `<amount> mcp-server(s) with <amount> tool(s) declared in "<file>"` in the log of the server is
  what states whether the declaration was found
